# Lendsqr Fintech MVP - Wallet Service

This repository contains the foundational setup and database schema for a production-ready fintech wallet service. The system is built with ExpressJS, TypeScript, KnexJS, and MySQL.

## Database Schema & Architecture

The database is built on strict **double-entry accounting principles** to ensure robust traceability, idempotency, and absolute precision with money.

### Core Tables

#### 1. `users`
Stores user identity information.
- **`id` (UUID)**: Primary key.
- **`email` & `phone`**: Unique constraints to prevent duplicate accounts.
- **`is_active`**: Boolean to manage soft-ban logic at the application layer.
- **`pin_hash`**: Hashed 4-digit user pin.
- **`password_hash`**: Hashed user password.

#### 2. `wallets`
Represents the cached, current state of a user's funds. 
- **`user_id` (UUID)**: 1:1 Relationship with `users`. **`ON DELETE RESTRICT`**.
- **`balance`**: Stored as `DECIMAL(18,2)`.
- **`currency`**: Defaulted to `NGN`.
- **`status`**: Enum (`ACTIVE`, `FROZEN`) to halt operations dynamically.

#### 3. `transactions`
The high-level representation of an action taken by a user (e.g., funding, withdrawing, or transferring).
- **`type`**: Enum (`FUND`, `TRANSFER`, `WITHDRAWAL`).
- **`amount`**: `DECIMAL(18,2)`.
- **`desription`**: A nullable field stating transacton purpose.
- **`reference`**: A unique string generated by the application. Enforces idempotency to prevent duplicate charges if an API call fails or is retried.
- **`sender_wallet_id` / `receiver_wallet_id`**: Foreign keys linking back to `wallets` with **`ON DELETE RESTRICT`**.

#### 4. `ledger_entries`
The immutable, append-only **Source of Truth** for the entire financial system. Every `transaction` spawns one or more `ledger_entries`.
- **`transaction_id`**: Links to the overarching transaction.
- **`wallet_id`**: Links to the specific wallet affected.
- **`direction`**: Enum (`CREDIT`, `DEBIT`).
- **`amount`, `balance_before`, `balance_after`**: `DECIMAL(18,2)` explicitly recording the exact delta and state of the wallet at the time of the ledger creation.

#### 5. `blacklist_checks`
A metadata table for storing external KYC/Blacklist API responses (e.g. Karma API).
- **`user_id`**: 1:1 relationship with `users`. **`ON DELETE CASCADE`** is used here because this is transient, non-financial data.

## Design Decisions & Rationale

### 1. `DECIMAL(18,2)` vs `FLOAT`
Monetary values are strictly stored as `DECIMAL(18,2)`. Using `FLOAT` or `REAL` types for money introduces catastrophic precision loss during rounding and calculations (e.g., `0.1 + 0.2 = 0.30000000000000004`). Decimal guarantees absolute precision.

### 2. Double-Entry Accounting
We separate **Transactions** (intent) from **Ledger Entries** (actual fund movement).
If User A transfers 500 NGN to User B:
1. One `transaction` record is created representing the 500 NGN transfer.
2. Two `ledger_entries` are created: 
   - A `DEBIT` of 500 from User A's wallet.
   - A `CREDIT` of 500 to User B's wallet.

This system guarantees that money is never created or destroyed out of thin air, but merely moved between entities. The `wallets.balance` is simply a cache that should always match the sum of a wallet's `ledger_entries`.

### 3. Immutable Ledgers
The `ledger_entries` table only has a `created_at` timestamp. It lacks an `updated_at` column by design. Financial ledgers are append-only. To undo an action, a new counterbalancing transaction must be posted.

### 4. `ON DELETE RESTRICT`
All financial relationships (`wallets`, `transactions`, `ledger_entries`) enforce `RESTRICT` deletion rules. If a user record is ever deleted, the database will throw an error. Financial history must remain intact for auditing and compliance reasons. Soft-deletes should be implemented at the application level instead.

### 5. Idempotency Keys
The `transactions` table requires a unique `reference`. This ensures that network retries from a client won't result in double charges.

### 6. UUID Primary Keys
Instead of auto-incrementing integers, UUIDs are generated at the database level. This prevents competitors from guessing user counts, prevents ID collisions in distributed systems, and makes data migration safer.

## Getting Started

1. **Install Dependencies**: `npm install`
2. **Setup Environment**: Copy `.env.example` to `.env` and fill in your DB credentials.
3. **Run Migrations**: `npm run migrate`
4. **Start Development Server**: `npm run dev`
